# Workflow input reference

This is the complete input contract for every harness workflow definition in this repository.
It is derived from the workflow definitions in `workers/workflows/`: an input is **required**
when it is listed in `inputParameters` and has no value in `inputTemplate`; every other listed
input is **optional**, with the shown default. Internal workflows are included for operators and
tests, but normally only the user-facing workflows are started directly.

Empty strings mean “use the normal runtime default” for that field. Model fields are blank by
default so the selected model profile can resolve them; do not replace them with a provider
default unless you are deliberately overriding the profile. `*PromptTemplateSource` records the
provenance of its companion override.

The following optional policy envelope is available on **every** workflow and is listed here once
rather than repeated in every optional-parameter line below:

- `modelProfile` defaults to `""`; pass a profile name (for example,
  `anthropic-standard` or `openai-standard`) or leave it blank for the configured default. TUI
  launches snapshot `/models` in that case; raw API/CLI callers retain bundled/repository defaulting.
- `modelPolicy` defaults to `{}` and carries the selected one-file user-policy snapshot.
- `modelPolicySource`, `modelPolicySha256`, and `modelsConfig` default to `""`; they record the
  snapshot provenance and optionally select a contained repository policy path.
- `modelOverrides` defaults to `{}` for explicit structured role overrides.

Every workflow resolves this envelope before agent work. The resulting role tier is carried into
sub-workflows, dynamic forks, and scheduled children; workers record the selected profile, role,
model, and source hashes in their task output. A nonblank legacy backend/model field remains an
explicit override for that task role.

**A `repoPath` does not have to be a git repository yet.** Point any workflow at an existing
directory — empty, or holding files that were never committed — and the first step that touches it
makes it a repository: `git init`, a local identity when none is configured, and an empty base commit
that leaves the directory's own files exactly as they were (uncommitted). The agent worker does this
before it reads `HEAD` (`coding_agent` output `initializedRepo`), so a program's planner or an
intake classifier never fails on a fresh directory; `cc_program`'s first step (`repo_memory_read`) and
the workspace steps (`workspace_prepare`, `prepare_repo`) do the same. A directory inside an existing
repository belongs to that repository and is left alone, and a path that does not exist is refused,
never created. Before this, run `edc1c893` failed four times on `git rev-parse HEAD` in an empty
directory and ended before planning.

## `address_pr_approval` (internal)

`address_pr`'s human-approval gate for one already-verified candidate, extracted to its own sub-workflow to keep `address_pr`'s own graph small. A verified candidate is never auto-published: the `address_gate` `WAIT` task always pauses for an explicit human `approve`/`revise`/`stop` decision, offering up to `maxApprovalRevisions` bounded, independently re-verified revision rounds first (each `revise` reruns `code_parallel`, marked `optional: true` so an infra failure there degrades to `verification_blocked` rather than failing the whole `address_pr` run). ## `test_cycle` (internal)

Required: `repoPath`, `candidateCommit`.

Optional: `testMode` = `"targeted"`; `maxFixAttempts` = `4`; `testCommands` = `[]`; `testPlanTemplate` = `""`; `testPlanTemplateSource` = `""`; `allowHeavySuites` = `false`; `includeBrowserTests` = `false`; `priorVerification` = `{}`; `allowedWriteRoots` = `[]`; `agent` = `""`; `model` = `""`; `maxTurns` = `250`; `maxBudgetUsd` = `50`; `repairPromptTemplate` = `""`; `repairPromptTemplateSource` = `""`; `sandboxChecks` = `false`; `sharedTree` = `false`.

Runs the repository's tests for one exact candidate commit and fixes what fails. `testMode` = `"targeted"` derives an exact-test or affected-unit plan from the candidate's diff; `testMode` = `"full"` runs the repository-wide suite and is the mode to use before publishing a PR — full mode reruns the whole suite on every repair iteration, so reserve it for a final pre-publication gate, not a review-feedback loop. `allowHeavySuites` is honoured only in full mode and is what permits an integration or end-to-end target; it is never inferred. `includeBrowserTests` is also full-mode-only and adds the repository's dedicated Playwright/Cypress script when one exists — it never triggers a browser install: if binaries are not already provisioned on the host, this reports a diagnostic in `rejectedCandidates` rather than blocking the run. `testCommands` and `testPlanTemplate` are the two forms of the operator override and both outrank every other source: `testCommands` is a structured argv list; `testPlanTemplate` is the same shape as an inline JSON string, for a caller that only has text to pass, and is rejected outright if it starts with `@` (the templating convention for resolving from a file in the checkout, which the candidate controls) rather than falling back to it. When both are supplied, `testCommands` wins, since it cannot suffer a JSON-parsing surprise. Below the operator override, discovery climbs a ladder and never blocks: the exact tests the changed files map to (`.conductor-code/verification.json` rules, then the per-language planners), then the affected package's own test command, then the repository suite (the command documented in the agent guide, then build-system inference, a heavy suite last). A candidate that changes only documentation ends `no_tests_required`; a repository with no test command at all ends `no_tests_found` with the reason named. Both count as passed because nothing could fail. `sharedTree` (set by `code_subtask` for a team's one shared tree) runs the commands in `repoPath` itself, with no clone and no install step, and the repair session edits that tree without resetting it: a clone of one item's commit has neither the teammates' files nor the installed dependencies, and a reset discards the teammates' commits (run `c6c1e7a7`). Repair writes are restricted to `allowedWriteRoots` — handed to `test_discover`, whose `repairScope` the repair agent runs under — falling back to the discovered changed-scope directories only when the caller declares none. The declared scope was received and never forwarded: a fork's repair agent scoped to the whole `store/` directory implemented sibling items' files to make the item's own acceptance test pass, and those commits collided with the owners' forks at integration (run `a33d7061`).

The budget is `maxFixAttempts` fixes and one more test run than that, capped at 4 and 5. Because each loop iteration is fix-then-verify, the final run is always a verdict and no fix is ever left unvalidated. The loop also stops early when a fix produces no new commit, since re-running would repeat the identical result.

**This workflow never fails.** Every terminal condition completes with a `testCycleState` the caller branches on: `tests_passed`, `no_tests_required`, `no_tests_found`, `tests_failed_after_fix_budget`, `tests_failed_fix_unavailable`, `runtime_unavailable`, `candidate_commit_missing`, `verification_input_invalid`, or `verifier_worker_unavailable`. `testsPassed` is the boolean for a SWITCH gate.

One caveat: never failing is not the same as always completing. There are no execution deadlines anywhere in this harness, so if the isolated verification worker is not polling, `test_discover` and `test_run` never start and the workflow stays RUNNING rather than reporting `verifier_worker_unavailable` — that state only fires when a task actually fails. A caller that needs a bounded answer must watch queue depth or `verification_health`, not this workflow.

It owns no branch: fixes are committed to whatever branch `repoPath` is checked out on.

**One run per code and command.** Every check launched through `verify_candidate` (a fork's test gate, the acceptance red run, the integration check, a team's or a program's final cycle, the Architect's checks) is remembered in the repository's dependency cache per code tree (every blob except `.cc/`), argv, sandbox and scope, and reused by any later caller on the same code (`reused`, `reusedFrom` on the command; `reusedCommands` on the run). Only a completed run is remembered (passed or `code_failed`, never an infrastructure block); `CONDUCTOR_CHECK_MEMO=0` turns it off. One frozen acceptance test ran four times at one code in a one-item program (its red run, the team's final cycle, the program's final cycle, the Architect's pass after a `.cc/`-only commit; run `993dce38`). The `go` directive of `go.mod` is read as a minimum (`>=1.21`), never a toolchain pin: read as a bare version it refused go 1.26 as `runtime_unavailable` and a program's integration check stayed red at every head (run `3c84dd5d`).

The disposable verification clone carries the source worktree's git-excluded tool cache (`.cc-cache/`: a scout's Playwright and Chromium, the npm and pip caches) by hard link, and a dependency install precedes the commands: the project's own runner (`npm test`) gets the install of the directory it targets, any other runner (a pytest acceptance test that drives `npm test`, `npm run build` and the scenario script) gets every manifest's install, each once, and a self-resolving toolchain (`go`, `cargo`, Gradle, Maven) none. Before this a frozen pytest test ran in a clone with no node_modules, failed with "vitest: command not found" and the scenario found no Playwright, and a test repairer spent three minutes on an environment it could not fix (run `f83293f5`).

## `publish_verified_pr` (internal)

Required: `repoPath`, `repo`, `headRepo`, `prNumber`, `branch`, `expectedHeadSha`, `candidateCommit`.

Optional: `replyBody` = `""`; `reconcileModel` = `""`; `reconcileMaxResolutionAttempts` = `3`; `reconcileMaxBudgetUsd` = `50.0`. The caller must approve and locally verify the candidate first. This workflow performs the one candidate guard, remote-head guard, exact commit push, and success comment -- it completes once the branch is updated and does not wait on or poll CI; GitHub's own PR page reports check status independently.

When the remote-head guard finds the PR branch has moved since the candidate was checked out, it does not simply give up: it merges the remote's new commits in (`reconcile_branch_drift`, agent-resolved on conflict, bounded by `reconcileMaxResolutionAttempts`). A clean merge (the remote's changes never touched the candidate's own changed files) is trusted and pushed without re-verification; a resolved conflict is genuinely new content and is re-verified through `test_cycle` before it is ever trusted for publication (`publicationState: "conflict_verification_failed"` if that re-verification fails). Only resolution failing outright still reports `publicationState: "branch_drift"` with nothing pushed. `reconcileState`/`reconcileTokens`/`reconcileCostUsd` in the output report what happened, if anything.

After merging the subtask branches this runs `test_cycle` in targeted mode, so the candidate it hands back has been tested and, where possible, repaired. `maxFixAttempts` bounds that repair loop. The result is diagnostic: `testCycleState` and `testsPassed` are returned for the caller to gate on, and a red suite never withholds the candidate commit. correctly identifies the real top-level launcher; a caller that embeds `code_parallel`

**Testing after the merge.** The merged change is tested targeted when its files map to exact tests. When they do not and the repository has a whole-suite command, documented or inferred, `test_mode_select` runs that suite instead, and forks skip the agents that would look for or write a test of their own. The output separates delivery from proof: `verified` means planned, merged and delivered; `deliveredAndTested` also requires its tests to have passed, or the change to need none; `verdict` is `DELIVERED`, `DELIVERED_UNTESTED`, `TESTS_FAILED` or `INCOMPLETE`. The `single` and `parallel` routes of `sdlc_intake` report `delivered` from `deliveredAndTested`. `singleSubtask` folds the validated plan into one work item built by one agent; the `single` route sets it.

## `code_subtask` (internal)

Required: `repoPath`, `name`, `prompt`, `model`.

Optional: `allowedTools` = `[]`; `allowedWriteRoots` = `[]`; `acceptanceTests` = `[]`; `maxBudgetUsd` = `50`; `maxTurns` = `250`; `promptContext` = `{}`; `promptTemplate` = `""`; `promptTemplateSource` = `""`; `contextPaths` = `[]`; `specContextPath` = `""`; `templateKey` = `"code"`; `feedbackCorrelationId` = `""`; `feedbackItem` = `""`; `feedbackSince` = `0`; `feedbackEveryTurns` = `1`; `checkpointEveryTurns` = `0`; `testCommands` = `[]`; `outputSchema` = `{}`; `sandboxChecks` = `false`; `modelTier` = `0`; `feedbackRunId` = `""`; `feedbackTeam` = `""`; `promptPath` = `""`; `sharedTree` = `false`.

A session's report is bounded: `filesChanged` and `fileChanges` list no dependency or cache tree (`node_modules/`, a virtualenv, `__pycache__/`, `.cc-cache/`) and at most 400 paths (`filesChangedTotal` keeps the count), and the workflow's `lastAgentReport`/`lastAudit` variables capture only the fields the repair prompt reads (`structured`, `status`, `error`; the audit's state and path lists): an implementer's `npm install` put 2,960 `node_modules` paths in its report, the variable grew to 731 KB and Conductor refused it at its 256 KB limit, failing the item with its work done (run `a8167484`). Sandboxed sessions also get `npm_config_cache` and `PIP_CACHE_DIR` under the worktree's `.cc-cache/` beside Go's cache: `npm install` died on EPERM opening `~/.npm/_cacache`. `allowedWriteRoots` is both the write guard and the delivery audit's planned-paths set, minus `acceptanceTests`: the item's frozen acceptance tests are inside the write roots only so a wrong assertion can be amended, so the audit (`delivery_audit` and `code_subtask_delivery_outcome`, `optionalPaths`) never counts one left untouched as a missing delivery — every item with a frozen test was audited `incomplete_delivery` and ran three no-op repair agents per fork (run `a33d7061`, 15 of 16 forks). Nor is a planned path that is already in HEAD's tree and left unchanged (`presentPaths`): a review re-dispatch changes only what the reviewer asked for, and the item's other files were delivered by its earlier attempt (store-hashes ran three no-op repair agents for the `hashes.go` it had delivered a wave earlier, run `ec0fb6dc`). The audit lists every untracked file by itself, so the first files of a new directory are audited as files, not as one collapsed `resp/` entry that made every planned file "missing" (same run). An implementer that reports `pushback` instead of a change gets audit state `pushback` and no repair agent (the Lead decides the pushback at integration; a repair agent rewrote `reader.go` after resp-reader's pushback and the Lead then discarded that fork); the outcome state is `pushback`, never `passed`. Likewise an implementer that made no change because the shared branch already satisfies its item (a sibling delivered the work, usually inside the sibling's own file) reports `alreadySatisfied` with its evidence: audit and outcome state `satisfied`, no repair agent (six repair agents re-verified cmd-dispatch's prose claim, created nothing, and the item blocked as an empty delivery, run `90e5e3aa`); the team's peer reviewer decides the claim at integration. A claim made alongside actual changes is an ordinary delivery. The fork's `commit` stages only changes inside `allowedWriteRoots` plus `acceptanceTests`: the agent runner's guard refuses Write/Edit outside the roots, but Bash can write any file of the worktree (sv-cmd-decr removed a sibling's type declaration through Bash after the Edit tool refused it, run `ba2491ff`), so a change outside the roots is left unstaged and reported as `outsideScope` — merged into the fork's `deniedWrites`, the Lead's scope-widening evidence — never integrated as an edit nobody owns. `test_cycle`'s repair commit is confined to its `allowedWriteRoots` the same way.

**What git sees is the whole tree, and outputs stay messages.** The harness excludes generated directories (`node_modules/`, `target/`, `dist/`, `build/`, `__pycache__/` and the rest of `git._NON_PRODUCT_PATH_PARTS`) through the repository's `info/exclude` whenever a worktree or session starts, whatever the repository's own ignore files say; tracked files under them stay tracked. Output the harness parses (`exec.run`: `git status`, `git diff`, `gh api`) is captured whole, never cut to the check runner's 1 MB log tail. A path list read off the filesystem travels in a task output as a count and `git.PATH_SAMPLE` examples (`rejectedPaths` + `rejectedCount`), and any output field over 256 KB is named in `oversizedFields` and the task log. A planned file that is on disk but that git does not report is a `staging_fault`: the delivery audit names it, `code_subtask` runs no repair, and the team blocks the item with an escalation instead of a retry or a rescue; a planned file the repository's own ignore rules hide is named with its rule as a failure the repair agent fixes. Before this, an empty `frontend/.gitignore` and an `npm install` left 15,000 untracked files in a shared tree, its 2.8 MB `git status` was cut to the tail, six written backend files went unseen, eight agents in turn were sent to write them, and the 1 MB rejected-path lists their outputs carried pushed three team workflows past Conductor's 10 MB payload limit (run `a87e9ddb`).

## `convergence_spike`

Required: `repoPath`.

Optional: `subtasks` = `[]`; `contractPaths` = `[]`; `ceilingUsd` = `20`; `warnFraction` = `0.8`; `maxWaves` = `8`; `maxAttempts` = `2`; `codeModel` = `""`; `maxTurns` = `250`; `maxBudgetUsd` = `10`; `maxFixAttempts` = `2`; `branchRunId` = `""`; `inPlace` = `false`; `workspacePath` = `""`.

The roadmap Phase 1 H1/H4 convergence spike. `subtasks` is the pre-registered OVERLAPPING plan (`[{id, description, files}]`, files deliberately shared across items); `contractPaths` names the frozen contract the forks build against but must not edit. Dispatch runs in ownership-gated **waves** (`maxWaves` caps the loop): each wave dispatches only the items whose shared files are free — two agents never hold the same file concurrently — then `convergence_integrate` rebases that wave onto the moving shared head (never a big-bang merge), releases the wave's file ownership, and records each agent's real spend. A fork that delivers no commit or hits a rebase conflict is **re-queued for a later wave** (up to `maxAttempts` per item — the moving head is what lets a retry land); only a frozen-contract edit or an exhausted retry budget is a terminal reopen. `ceilingUsd` is the aggregate spend ceiling: the reused `budget_gate_check` enforces the not-startable rule (a swarm-mode run with `ceilingUsd <= 0` refuses to start, roadmap H5) and, once per-wave spend is recorded, **halts dispatch of further waves** when accumulated spend reaches the ceiling. The workflow emits an honest GO/NO-GO `verdict` and `report`; a NO-GO names the precise mechanism (rebase conflict, contract controlled-event, budget-halt undispatched items, or a non-green shared branch).

## `team_build`

Required: `repoPath`.

Optional: `subtasks` = `[]`; `contractPaths` = `[]`; `instruction` = `""`; `forceSingle` = `false`; `forceTeam` = `false`; `enablePeerReview` = `true`; `ceilingUsd` = `40`; `warnFraction` = `0.8`; `maxWaves` = `12`; `maxWidth` = `10`; `maxAttempts` = `2`; `maxReviewRounds` = `2`; `stallAttempts` = `2`; `qualityChanges` = `2`; `maxReviewAttempts` = `2`; `maxContractEvents` = `2`; `planUsage` = `{}`; `feedbackEveryTurns` = `1`; `checkpointEveryTurns` = `10`; `bestOf` = `1`; `authorAcceptanceTests` = `true`; `acceptanceTestPattern` = `"tests/acceptance/test_accept_{id}.py"`; `parentCorrelationId` = `""`; `subsystemId` = `""`; `maxHumanConstraints` = `3`; `sandboxChecks` = `true`; `codeModel` = `""`; `maxTurns` = `250`; `maxBudgetUsd` = `10`; `reviewMaxTurns` = `60`; `reviewMaxBudgetUsd` = `3`; `maxFixAttempts` = `2`; `branchName` = `"team-build"`; `branchRunId` = `""`; `inPlace` = `false`; `workspacePath` = `""`; `maxRescues` = `2`; `baseModelTier` = `0`.

The roadmap Phase 2 team cycle (with the Phase 3 monitor wired in): each wave a `team_monitor` watches the board with bounded authority — it nudges/re-prioritizes a thrashing item (`stallAttempts`) or a repeatedly-rejected one (`qualityChanges`) autonomously, and escalates anything bigger (a blocked item, duplication, a budget breach) to the exception queue for a human to drive from the web Swarm Console (`make console`). The roadmap Phase 2 team cycle: a collaborating agent team builds a multi-item feature on one shared branch. `subtasks` is the decomposed work (`[{id, title, description, kind, dependsOn, files, acceptanceCriteria, priority}]`); `contractPaths` names the frozen contract (H4). `team_route` first reads the mode off the decomposition (H9/H12): one small piece (or `forceSingle`) routes to plain `code_parallel` with **zero board overhead**; multi-item/coupled work (or `forceTeam`) runs the board cycle. The cycle is a `DO_WHILE` of **standup → fan out → implement ∥ review → integrate → learn → re-plan** over a mutable tracking board: each wave the Lead sizes the team from dependency-ready work (`maxWidth` caps it, throttled as spend nears the ceiling), gates dispatch on shared-file ownership (H1), and injects the live board rollup + teammates' lessons + the item's directives into each implementer. `team_integrate` rebases the wave onto the moving shared head (never a big-bang merge), records real spend, and moves clean items to peer review; a different agent reviews each item against its acceptance criteria (H8/H13) and `changes` reopens it with the findings attached (bounded by `maxReviewRounds`), `lgtm` marks it done and shares a lesson. `ceilingUsd` enforces the H5 not-startable rule and halts further waves on accumulated spend; `maxWaves` caps the loop; `maxAttempts` bounds transient (empty/conflict) retries. The workflow emits an honest `verdict` (DELIVERED / INCOMPLETE) and `report`; INCOMPLETE names the precise mechanism (blocked items, a budget halt leaving work undone, or a non-green shared branch).

Convergence and honesty rules (closure plan WP1): every item in review is reviewed; `maxReviewRounds` is how many `changes` verdicts an item may absorb, and the next one **quarantines** it (`blocked`, `review_rounds_exhausted`, exception `review_cap`) — a rejected item is never accepted silently; a reviewer that returns no verdict is `unavailable` (re-reviewed next wave, `blocked` after `maxReviewAttempts`). A fork that edits the frozen contract is a **controlled event**: it is never merged, its proposer is `blocked` with `contract_change_pending`, and the Lead rejects the edit at once (a frozen contract stays frozen; the next standup re-dispatches the proposer against the contract as-is, with that constraint); more than `maxContractEvents` proposals from one item block it as `contract_churn`. **Humans are passive observers of the swarm**: they watch, give feedback, and can terminate; nothing waits for their approval. Each wave ends with a liveness check: when no work can move, the run exits at once naming `dependency_starved` or the open escalations, instead of spinning empty waves to `maxWaves`. Before any implementer is dispatched (closure plan WP6, H13), every item with `acceptanceCriteria` gets its acceptance tests written by a **different** agent (`authorAcceptanceTests`, at `acceptanceTestPattern`); they are committed, run raw at the base, and only tests that are **red** before the feature exists are kept — a test that already passes is tautological and is discarded with a lesson. Kept tests join the frozen contract (an implementer's edit of its own check is a controlled event, never merged), pin that item's own test gate, and are checked byte-for-byte at the end: a delivered head where a frozen acceptance test was modified is never `DELIVERED`. Steering is identified and has a lifecycle (closure plan WP7, H16): a directive's authority is derived from its author — only a registered actor (`$SWARM_ACTORS_FILE`) writing as `human:<email>` ranks as a human — and a constraint can be lifted, replaced, or lapse after `expiresAfterWaves`; the monitor escalates an item carrying `maxHumanConstraints` or more human constraints, or failing while it carries any (`over_constrained`). An implementer that judges a constraint harmful or impossible reports `pushback` instead of silently obeying or overriding it: the Lead exempts that item from that one directive (it stays in force for everyone else), records the decision as a resolved `pushback` escalation, and re-dispatches the item (bounded by `maxAttempts`, after which it blocks as `constraint_pushback`). Implementers also report lessons, shared as `opinion` (never above medium confidence) until an outcome verifies them; a reviewer can `retract` a lesson its diff proves wrong, and a lesson whose `path` or `path::symbol` ref no longer resolves on the shared branch is dropped from every prompt (closure plan WP8, H10/H15). Every check command — the acceptance red run, each item's test gate, and the final suite — runs OS-sandboxed when `sandboxChecks` is on (the default here): writes confined to the disposable checkout and caches, no network but loopback (closure plan WP9, H17), except the dependency install and a build system that resolves dependencies while it builds (Maven, Gradle, Cargo, Go, dotnet, sbt: `verification._needs_network`), which get the registry — a sandboxed `mvn test` could fetch neither the parent POM nor the surefire plugin and three teams' every item ended `tests_failed_fix_unavailable`, run `afb90941`. With `bestOf` > 1 each dispatched item runs that many independent candidate forks under one ownership claim; the integrator keeps the best (delivered and contract-respecting, then subtask tests green, delivery audit passed, fewest files, smallest diff, lowest cost), integrates only it, and discards the rest (H12a: best-of-N inside the swarm). Every agent's spend — implementers, reviewers, the planner (`planUsage`), and final test-repair agents — is recorded on the run budget, and `spendByRole` reports it. Each implementer takes feedback **while it works** (closure plan WP2, H11): a directive posted to its item, `agent:<item>`, or `team` after its prompt was built is injected into the running session after its next tool call (`feedbackEveryTurns`, default every call); a `blocking` directive (the console's `stop`) ends the session, and the item is re-opened with the directive instead of integrating partial work. Every `checkpointEveryTurns` tool calls the implementer's worktree is snapshotted into `refs/cc-checkpoints/<branch>` (H17), and a session that starts on a clean worktree at that checkpoint's parent restores it, so a lost worker costs at most that many tool calls. The final green gate runs `test_cycle` in `full` mode: the integrated branch of several items is verified by the repository's whole documented suite, not only the paths the last change touched. Not every item is code: an item's `deliverable` is `code` or `docs` (design documents, specs, ADRs, research notes; inferred as `docs` when every file is a document) — a `docs` item gets a documents-first prompt, no executable acceptance tests, and a reviewer who is its only check. While it works each implementer posts a throttled `activity` heartbeat (its current tool and target), so the run's state can be asked at any time (`GET /api/state`, `POST /api/ask` on the Swarm Console). An implementer refused a file outside its write roots (the worktree guard records it as `deniedWrites` on the fork's output and the integrator on the item's `session` fact) tells the Lead the plan sliced the item too narrowly: at the next standup the item's write scope is widened to that file once no open item still owns it (a resolved `write_scope` notice records it, and the reviewer's diff covers the file), the item waits while an open item still owns it (`scopeWaits`), and a frozen-contract path is never widened — resubmitting work-arounds against the review cap is what halted the resp-cache program (run `fc6467b7`, st-lru / `store/store.go`). A team's write authority ends at the directories its items span: a refused path outside them is never widened (`scopeRefusals`, a resolved `write_scope` notice) — the design team's d-store, a documents item, was widened to `store/errors.go` and `store/store.go` and took ownership of code the breakdown then assigned to the store team (run `a33d7061`); writing outside the subsystem is the program's call. A rebase conflict's mechanism names the shared-branch commit that last changed each conflicting file (`touched`), so the other side of the collision is visible at once. A wave's `finalHead` is read after `team_apply_reviews` (its `finalHead` output), not from the integrate step: an approved acceptance-test amendment is merged by apply_reviews, after integration, and the final test cycle's candidate and the outcome's byte-for-byte check must see that head — the server team re-froze its amended test at the merged head and was judged "modified after frozen" against the integrate step's stale head, blocking cmd and integration on a delivered subsystem (run `ec0fb6dc`). Fork worktrees are short-lived: once the wave has decided a fork — integrated, re-queued, or discarded — the integrator removes its worktree and branch (`removedForks`; the work is on the shared branch, a re-dispatch starts a fresh fork from `refs/cc-checkpoints`), and only a fork held for an acceptance-test amendment keeps its worktree until the reviewer decides. Implementers run with the full unattended tool surface (`DEFAULT_ALLOWED_TOOLS`: the language build/test/format entrypoints, `make`, file utilities), so a repository's documented verification command is runnable from inside a fork. A frozen acceptance test is proven on its item's fork alone, so after each wave's merges the integrator re-runs every integrated item's frozen tests at the integrated head (the **integration check**, `check` on `team_integrate`: `{state, checked, red}`; sandboxed under `sandboxChecks`): an item whose test is red there is re-opened (`integration_check_red`, bounded by `maxAttempts`) with the failing output as its directive — its re-dispatch fixes the code, or amends an assertion a sibling's landing falsified, which the peer reviewer decides as any amendment — and a fork held for an amendment is not checked (its test is red at the head by construction). Acceptance-test authors are told never to assert a sibling's behaviour is absent. An empty delivery whose implementer reports `alreadySatisfied` (its registry and dispatch already written by a sibling inside the sibling's file) is not retried blind: the integrator posts an empty delivery range at the current head with the claim (`claimedSatisfied`), the item goes to peer review, and the reviewer judges the claim against the criteria on the current tree — `lgtm` is done as-is, `changes` names what is missing or misplaced and re-opens the item as any review would; with peer review disabled it stays an empty delivery. **The model ladder adapts (hill climbing).** A role's tiers are a ladder, cheapest first (the bundled code ladder: Sonnet at medium effort, Sonnet at high, Opus at high). Each item starts on the cheapest rung that has got its kind of work (`docs`, `scaffold`, `module`, `wiring`: `rung_policy.item_kind`) done on this repository, and after a success the next item of that kind probes one rung cheaper; a rung that failed is probed again after three wins on the rung above (`common/rung_policy`). Inside an item, help climbs one rung per agent-fixable failure (a red check, review rounds exhausted, a rebase conflict); a session that never completed (`agent_unavailable`), a harness fault (`staging_fault`) or a reviewer that never answered retries on the same rung, since a stronger model cannot fix it. `team_outcome` records each item's attempts as `rung_outcome` facts on the `_rung_outcomes` board (`rungOutcomes` on its output), keyed by the repository every worktree of it shares, and the console shows each item's rung and why. The Architect (`plan`: planning, the breakdown and every evaluation) has its own ladder, Opus 5.5 at medium then high: a replan runs the planner a rung up (`modelTier` = the plan loop's iteration with `modelTierOrigin` 1) and an evaluation climbs with the repair rounds (`tier`). Measured on one planner prompt (run `8ab37c0f`): Opus 4.8 took 383 to 408 s at high effort and 400 s at medium, Opus 5.5 305 s at high and 147 s at medium ($0.44 against $1.02); an implementer replayed from its starting commit through the sandboxed runner (run `8ab37c0f`, the backend scaffold) took 123 to 132 s on Sonnet 5 and 46 s on Sonnet 5.5 at medium, so the bundled code ladder is Sonnet 5.5 medium, Sonnet 5.5 high, Opus 5.5 high. Sessions run the newer of the agent SDK's bundled Claude CLI and the host's (`coding_agent.claude_cli`, override `CONDUCTOR_CLAUDE_CLI`): the bundled 2.1.208 could not run Opus 5.5. Before this every item started at the bottom and a stuck one ended on Opus with nothing learned, and a harness fault that looked like a stuck agent sent 32 sessions of run `a87e9ddb` up to Opus at high effort.

**Help for a struggling agent.** A swarm does not give up on an item its agents are stuck on. Wherever an item used to block — attempts exhausted on an empty delivery, a rebase conflict or a red integration check, review rounds exhausted with findings unaddressed, a pushback that could not be resolved, frozen-contract churn, a reviewer that never returned a verdict — the Lead first reopens it with a fresh attempt budget (a resolved `rescue` notice; `rescued` on `team_integrate` and `team_apply_reviews`) and the next standup hands it to a stronger teammate: the next tier of the code role's model policy (`modelTier`, passed through `code_subtask` to every agent; tiers are ordered, the first is the default and the index is clamped to the last; a tier carries the reasoning `effort` it runs at, so the bundled ladder is Sonnet at medium, Sonnet at high, then Opus at high, while the Architect's `design` and `plan` roles always run high — the planner at the CLI's default effort spent 215 of its 317 s thinking, run `8fb0cf98`), briefed as the help for a stuck item and given the item's full history — every dispatch, delivery outcome, review finding, failure mechanism, pushback, refused write and directive — with the instruction to find the root cause rather than repeat what failed. Review rounds restart for the helper. Each helper runs a tier higher, up to `maxRescues` tiers above the first try (then the strongest reached; `0` turns help off), and help keeps coming until the work lands or the run reaches its budget or wave limit. A helper may change any file in the repository, is never held or refused on write scope, and may correct a frozen test or contract: with peer review on the reviewer approves or rejects it, with peer review off the Lead merges it; its reviewer reads the whole diff. A reviewer that returned no verdict re-reviews a tier up, and a team its program re-runs starts every agent one tier up (`baseModelTier`). The ladder is: retry with feedback, a stronger teammate with the history, the program re-running the team with its diagnosis, with the Lead breaking any board-level deadlock itself: `team_monitor` assigns a helper to each stuck root and drops exactly the dependencies that can never land (on no item of the board, or on a cycle).


**Result branch.** `branchName` names the branch a run's work lands on; the run's short id is appended so two runs never share one (`swarm/pg-compatible-database-037e1cbe`). The console fills it from the request (`swarm/<words of the request>`); left at the default the branch is `team-build-<run id>`. The run's checkout under `.cc-worktrees/` holds the branch until a follow-up run continues from it (Continue takes the branch over from a finished run's clean checkout) or the next run on the repository prunes finished runs' checkouts; the branch keeps every commit either way, and `git log`, `git diff` and `git merge` on it work from your own checkout.

## `sdlc_intake`

The roadmap Phase 5 (G3) greenfield on-ramp. `sdlc_intake` routes a request it classifies as `greenfield` here, with the normalized request as `firstFeature`. ## `swarm`

Required: `repoPath`, `description`.

Optional: `branchName` = `""`; `maxRounds` = `8`; `maxWidth` = `10`; `ceilingUsd` = `60`.

The simple swarm. The harness provisions, fans out, measures and loops; every judgment is an agent's. `swarm_setup` makes a private clone of `repoPath` under `.cc-worktrees/swarm-<run>` on branch `<branchName>-<run>` (blank: `swarm/<words of the request>-<run>`). An architect `coding_agent` (role `design`, prompt `swarm_plan`) writes `.cc/design.md` and the acceptance checks (`.cc/checks.json`, each proven red on the untouched tree) and splits the work into items. Each round, `swarm_dispatch` starts one `coding_agent` per item (role `code`, prompt `swarm_work`, at most `maxWidth`) in the SAME clone: agents read each other's work as it lands, coordinate on the board, and reason about whatever blocks them (a teammate's broken file, a port in use, a check they believe wrong); they do not commit. ## `ship_run`

Required: `repoPath`, `branch`, `head`, `title`.

Optional: `base` = `""`; `summary` = `""`; `draft` = `false`; `remote` = `"origin"`.

Ships a finished swarm run: `git_push` pushes the run's result branch to `remote`, bound to `head` (the commit the result card showed; a branch that moved since is refused), then `pr_create` opens a pull request from it into `base` (empty: the repository's default branch), with `summary` as the body's single Summary paragraph.
