## Context

`code_parallel.json` plans via `openspec_plan` (which produces `proposal.md`/`design.md`/`specs/**`/`tasks.md` under an OpenSpec change directory and reviews them through a human-or-AI-judge loop), then fans `tasks.md`'s independent task groups out to parallel `code_subtask` workers, and merges their branches back with `merge_worktrees`. That's where `code_parallel.json` currently stops.

Two workflows call `code_parallel` directly and are the actual production path for "resolve this and open a PR": `issue_to_pr.json` (GitHub issue → PR) and `address_pr.json` (PR review feedback → updated PR). Both go straight from the `code_parallel` sub-workflow's output to `git_push`/`pr_create`. Neither references `openspec_finalize`, `openspec_verify`, or archiving anywhere.

A third, separate workflow, `openspec_development.json`, imports an *existing* external OpenSpec change (not one `code_parallel` just planned) and does have a verify/archive gate: `openspec_semantic_verify` (an LLM judge) feeds `openspec_verify`, which gates a `verified_gate` `SWITCH` — on `true` it calls `openspec_finalize` (`coding-harness/workers/openspec/tasks.py:588-631`), which flips `tasks.md` checkboxes to `[x]` (`_complete_tasks`), runs `openspec validate <id> --strict --no-interactive --json`, then `openspec archive <id> --yes`, then commits. On `false` it just sets `outcome = "needs_attention"` and the workflow ends — no retry, no PR. This sequence is correct and working, but it's wired into a workflow that `issue_to_pr`/`address_pr` don't use.

Ahead of this change, two new worker tasks were added speculatively (`openspec_change_validation`, `openspec_archive` in `coding-harness/workers/openspecops/tasks.py`, backed by `validate_changes`/`archive` in `coding-harness/workers/common/openspec_cli.py`) that call the OpenSpec CLI with a different, unverified argument shape (`--change <name>` instead of positional id, no `--yes`, no checkbox-completion step first) and duplicate `openspec_finalize`'s job without its proven correctness. This design supersedes them.

Separately, `coding_agent` (`coding-harness/workers/common/coding_agent.py:470-471`) resolves its runtime tool policy as `allowed_tools if allowed_tools is not None else DEFAULT_ALLOWED_TOOLS` — passing `allowedTools` **replaces** the default list rather than extending it. `DEFAULT_ALLOWED_TOOLS` (`coding-harness/workers/common/tool_policy.py`) already scopes in `pytest`/`npm`/`npx`/`go`/`cargo`/etc. as Bash prefix patterns, but a project whose `tasks.md`-declared `Test:` command is something else (`make check`, a repo script) would have that command silently denied under the `dontAsk` permission mode used throughout — the agent gets no prompt, the command is just refused.

## Goals / Non-Goals

**Goals:**
- After `code_parallel`'s fan-out and merge, actually verify the merged result before it can become a PR: run each subtask's declared test for real, and judge the diff against the OpenSpec artifacts.
- Give that verification (and a bounded fixup pass) a real chance to run the project's actual test commands, including ones outside the small default allowlist.
- On success, leave the OpenSpec change's planning artifacts in place in the repo (and therefore in the PR diff) for reviewer visibility — archiving them is an out-of-band step a human performs after the PR merges, not something this change automates.
- On failure (after bounded retries), fail closed: no push, no PR.
- Make this behavior a property of `code_parallel.json` itself so `issue_to_pr` and `address_pr` inherit it without per-workflow duplication.
- Give human reviewers (via `plan_review`) and PR readers (via the PR body) the actual proposal content and real verification/cost data, not a pointer to files or a boilerplate sentence.

**Non-Goals:**
- Not changing `openspec_development.json`'s own verify/finalize gate — it already works for its (different) entry point; this change does not touch it at all, and does not call it.
- Not automating post-merge archival — no PR-merge webhook or poller is introduced by this change; running `openspec archive` after a PR merges is a manual command a human runs (or the subject of a possible follow-up change).
- Not re-foragating the whole fan-out on a verification failure — retries are a single consolidated fixup pass, not a re-plan or a re-fork of all subtasks.
- Not adding an LLM-authored PR body — the PR body is assembled by a deterministic `JSON_JQ_TRANSFORM`, not a coding-agent summarization call.
- Not solving arbitrary shell-command allowlisting in general — only the specific, already-declared-in-`tasks.md` `Test:` command per subtask gets an allowance; this is not a general escape hatch for the fixup agent.
- Not embedding `design.md` (only `proposal.md`) in the human review draft — `design.md` can be long; verbatim embedding is scoped to the short artifact.

## Decisions

**Decision 1 — Add the verification loop and archive step inside `code_parallel.json`, after `merge_worktrees`, rather than at each caller.**
`issue_to_pr` and `address_pr` both call `code_parallel` as their entire implementation engine and both currently skip verification/archival identically. Putting the gate in the sub-workflow means both callers get it for free and can't drift out of sync. *Alternative considered:* add the gate to each caller workflow individually — rejected, since it duplicates the same DO_WHILE/SWITCH structure twice and a third caller would need it a third time.

**Decision 2 — Verification loop is `DO_WHILE`, modeled on `openspec_plan.json`'s existing `openspec_loop` fail-closed pattern, not a new mechanism.**
`openspec_plan.json`'s loop condition (`iteration < max && !approved`) and its `TERMINATE` on exhaustion is a pattern this codebase already trusts. The new `verify_loop` uses the same shape: `iteration < maxVerifyIterations && !passed`, terminating with no archive/PR if never satisfied. *Alternative considered:* a fixed number of sequential SWITCH/retry blocks unrolled at authoring time — rejected as harder to bound/tune and inconsistent with the existing loop idiom.

**Decision 3 — Verification combines real test execution and a semantic judge, mirroring `openspec_development.json`'s existing `openspec_verify` formula (`semantic.passed && checksPassed`), not either alone.**
Running only the declared `Test:` commands catches functional regressions but nothing about whether the change actually satisfies `tasks.md`/`specs/**` (e.g., a task silently skipped, requirements reinterpreted narrowly). Running only a semantic judge catches spec-fidelity issues but can't see runtime failures the judge doesn't re-execute. Both together, combined with AND, matches the existing `openspec_verify` task's logic (`coding-harness/workers/openspec/tasks.py:562-578`) applied to the `code_parallel` path instead of the `openspec_development` path. *Alternative considered:* judge-only (cheaper, one fewer step) — rejected because it lets a plausible-sounding but non-functional diff pass.

**Decision 4 — On failure, run one consolidated fixup `coding_agent` against the already-merged worktree, not a re-fork of the implicated subtasks.**
Re-deriving which subtask "owns" a failing test or judge finding and re-opening its worktree reintroduces merge-conflict risk and re-parallelizes what should, at this stage, be a small delta. A single fixup pass (modeled on `code_revision_loop.json`'s produce/checkpoint/evaluate shape, minus its restore-best mechanics since there's one branch, not competing candidates) gets the failing test output and judge findings directly, fixes them in place, and re-runs the same checks. *Alternative considered:* re-fork only the subtasks whose declared `files` overlap the failing test/finding — rejected for this change as materially more complex (requires attributing a failure to a specific subtask, which the semantic judge's findings don't reliably do) and deferred as a possible follow-up if fixup cost becomes a problem in practice.

**Decision 5 — Explicitly pass `DEFAULT_ALLOWED_TOOLS` plus a derived pattern for the subtask's own `Test:` command as `allowedTools`, computed once per subtask and reused for both the original and fixup `coding_agent` calls.**
Because `allowedTools` replaces rather than merges, the only safe way to add one command is to enumerate the full desired set explicitly at the call site (in `build_forks`'s `JSON_JQ_TRANSFORM`, alongside where `testCmd` is already extracted). The derived pattern is the `Test:` command's first whitespace-delimited token turned into `Bash(<token> *)` — e.g. `make check` → `Bash(make *)`. Known limitation, not solved here: a compound command like `cd tests && pytest` won't match (its literal first token is `cd`, which isn't in `DEFAULT_ALLOWED_TOOLS`); this is documented as a constraint on `Test:` command authoring (single invocation, no `cd`/`&&` chaining) rather than solved with a shell-parsing allowlist generator. *Alternative considered:* allow bare `Bash` unscoped for verification-related agent calls — rejected as a much larger permission surface than the one command actually needed, contrary to the harness's existing scoped-allowlist design.

**Decision 6 — Remove the two bespoke tasks added ahead of this change; do not call `openspec_finalize` (or anything else) to archive from `code_parallel` at all.**
The two speculative tasks (`openspec_change_validation`/`openspec_archive`) reinvent `openspec_finalize`'s sequence with a different, unverified argument shape, skip checkbox completion, and were never wired into any workflow — removing them is correct on its own merits regardless of where (or whether) archiving happens, so this change still deletes them and their CLI wrapper functions. What changed from the original version of this decision: `code_parallel.json` was initially going to call `openspec_finalize` directly to archive once the verification loop passed, reusing its proven sequence exactly as `openspec_development.json` already does. Live runs against a real sandbox repo hit `openspec archive`-time failures repeatedly (see "Post-implementation fixes" below) — each fix closed one concrete failure mode and the next live run found another. Rather than continue chasing archive-specific correctness inside a loop whose actual job is verifying the *code*, the decision was reversed: `code_parallel` (and therefore `issue_to_pr`/`address_pr`) never calls archive, ever. `openspec_finalize` itself is untouched and keeps serving only `openspec_development.json`'s separate, already-working entry point. *Alternative considered:* keep iterating on archive-failure handling inside `verify_loop` (adding another special-cased fixup remedy each time a new archive failure mode surfaces) — rejected as an open-ended, low-signal debugging loop for a step that isn't on the critical path of getting a correct PR opened; a human merging the PR is a natural, low-cost point to run `openspec archive` once, where any failure is visible and interactive rather than silently swallowed by an unattended fixup agent. *Also considered:* keep the two bespoke tasks and just fix their flags — rejected as before, and now doubly moot since neither path archives from `code_parallel`.

**Decision 7 — `plan_review`'s draft embeds `proposal.md` verbatim; PR bodies are assembled by a deterministic `JSON_JQ_TRANSFORM`, not an LLM.**
`proposal.md` is short by convention (the proposal-artifact instruction itself asks for "1-2 pages"), so verbatim embedding in the `WAIT` draft's `inputParameters` is cheap and keeps the reviewer's context self-contained. The TUI's `ApprovalModal._draft_text` needs a corresponding rendering addition for this new field on the `openspec_plan` draft kind. For PR bodies, the user explicitly wants a predictable, strongly-formatted structure over freeform prose, and `issue_to_pr.json` already has a working example of this shape (`final_pr`'s `JSON_JQ_TRANSFORM`, `issue_to_pr.json:138-148`) that this change extends with more input fields rather than replacing its mechanism.

## Post-implementation fixes

Found while running the shipped change against a live sandbox repo (a `hello.py` change whose `tasks.md` declared `Test: python hello.py ...` on a host with only `python3` on `PATH`):

- **`openspec_run_subtask_check` treated a launch failure as a worker crash, not a check failure.** `subprocess.run` raises `FileNotFoundError` (via `OSError`) when the command's binary doesn't exist, *before* it ever produces a returncode. The original code's blanket `except Exception: return fail(...)` turned that into a Conductor `FAILED` task status. Since `checks_fan_out`'s dynamically-forked tasks are not `optional` and have `retryCount: 0`, this aborted the entire `code_parallel` run before the verification loop's fixup pass ever got a turn — exactly the class of failure the fixup loop exists to handle. Fixed by catching `OSError` specifically around the `subprocess.run` call and returning `{"passed": false, ...}` via `ok()`, so a missing/misnamed binary is just another check failure the loop can act on.
- **`checksList` was captured once before the loop and never refreshed, so a fixup could never actually be verified.** `build_forks` computed `checksList` from the plan-time `subtasks[]` snapshot, and `verify_loop`'s `build_checks` step reused that same static value on every iteration. Once the launch-failure bug above was fixed, this second bug would have surfaced immediately after: if the fixup agent corrected `tasks.md`'s `Test: python ...` line to `Test: python3 ...`, the next round would still re-run the *original* `python` command and fail identically until `verifyMaxIterations` exhausted — the loop could never converge on any fix that touched a declared `Test:` line. Fixed by adding a `reparse_tasks` (`openspec_tasks_to_subtasks`) call inside the loop, reading `${openspec_plan.output.changeDir}/tasks.md` fresh each iteration, and deriving `build_checks`'s `checksList` (and the fixup's `fixupAllowedTools` union, recomputed alongside it) from that live re-parse instead of `build_forks`'s stale snapshot.
- **`checks_summary` crashed with `Cannot index string with string "passed"`.** Its jq unwraps each `checks_join` entry via this codebase's established `.value.output // .value // {}` idiom (also used by `aggregate()`, needed because some FORK_JOIN_DYNAMIC/JOIN entries arrive pre-wrapped under an `output` key and some don't). `openspec_run_subtask_check`'s own output happened to also have a field literally named `output` (the captured stdout/stderr text) — so for a failing check, `.value.output` resolved to that *string* instead of `null`, `//` never fell through to the real object, and the later `.passed` lookup indexed a string. Fixed by renaming that field to `log`, removing the collision; the existing unwrap idiom in `checks_summary` needed no change.
- **The planning agent had no idea what commands the coding agent is actually allowed to run, so it wrote unrunnable `Test:` lines.** A live sandbox run produced `Test: test "$(python hello.py)" = "Hello, World!" && ...` — a compound shell one-liner using `test`/`&&`/`$(...)`, none of which are in `DEFAULT_ALLOWED_TOOLS` (and `test` never was, independent of this change), so the coding agent's attempt to self-verify with it was denied outright. Separately, even a `Test:` line using only allowed binaries but joined with `|`/`&&` (e.g. the earlier `python hello.py | grep -qx ... && python hello.py Alice | grep -qx ...`) would not execute as intended by `openspec_run_subtask_check` either: it runs the command via `shlex.split` + `subprocess.run` with **no shell**, matching this codebase's existing `campaign/checks.py` convention (deliberately avoiding `shell=True` to keep AI-authored command strings from becoming a shell-injection surface) — so shell operators are passed as literal, meaningless arguments to the first program instead of being interpreted. This wasn't a bug to patch downstream; it needed the source of the problem — the planning prompt — fixed. Extended `TASKS_RULE` (`common/openspec_cli.py`, already surfaced verbatim into the tasks-artifact-writing agent's prompt via `openspec_generate_artifact.json`'s `rules` plumbing) to state the constraint explicitly: `Test:` MUST be exactly one program invocation with no shell pipes/chaining/substitution/builtins, naming the concretely-allowed runners (`pytest`, `npm`, `npx`, `go`, `cargo`, `node`, `python3` — not `python`). Also added a short, complementary note to the `verify_judge` and `verify_fixup` prompts so that if a legacy/malformed `Test:` line still slips through, the judge attributes the failure correctly (a tasks.md defect, not a missing feature) and the fixup's remedy is to simplify the `Test:` line rather than work around the restriction.

- **`openspec archive` crashed the whole workflow when the spec itself was invalid.** `verify_gate` only ever checked real test execution + the semantic judge before calling `archive_change` (`openspec_finalize`). But `openspec_finalize` runs its own `openspec validate <id> --strict` immediately before archiving, and that call raises (via `_run`'s default `allow_failure=False`) on a genuinely invalid proposal/design/specs/tasks.md — a class of defect the loop had never checked for, so the loop could report `passed: true` and then crash moments later at archive time, with no chance for the fixup pass to correct the spec. Fixed by adding a new `openspec_validate_change` task (graceful — returns `{valid, issues}` via `ok()`, never raises) and running it every verify_loop iteration alongside the real test commands and the semantic judge; `verify_round`'s `passed` now requires all three (`checks.allPassed && judge.passed && specValid`), and a spec-validity failure surfaces as an `"OpenSpec validate failed: ..."` finding the fixup agent acts on (told explicitly to fix the flagged OpenSpec artifact, not the application code, unless the two genuinely disagree). `archive_change`'s own internal validate call is left as a final defense-in-depth check — by the time `verify_gate` calls it, this same validate has already passed within the last iteration, so it's now expected to be a no-op in practice.
- **`openspec archive` *still* crashed the workflow — a different failure `openspec validate` doesn't catch.** A live run failed with `openspec archive harness-issue-3 --yes failed ... current spec contains scenario(s) not present in the modified block: "..."` — an archive-time-only safety check (comparing the change's `## MODIFIED Requirements` block against the *current* main `openspec/specs/<capability>/spec.md`, refusing to silently drop a scenario on merge) that `openspec validate` does not perform. So `openspec_validate_change` above genuinely reported the spec valid, `verify_gate` proceeded, and `openspec_finalize`'s own internal `archive` call still raised and crashed the workflow with no chance for the fixup pass to run — the "defense-in-depth" call from the previous fix turned out to be load-bearing, not redundant. Fixed by restructuring so `archive_change` (still `openspec_finalize`, called the same way) runs **inside** `verify_loop` itself: the prior `verify_round` was renamed `verify_precheck` (unchanged logic — `checks && judge && specValid` — now called `preArchivePassed`), a new `archive_attempt_gate` SWITCH attempts the real archive only when `preArchivePassed` is true and marks the call `optional: true` so its failure can't crash the workflow, its result is captured into `workflow.variables` (`archived`/`archiveError`/...) via `capture_archive_result`/`capture_archive_skip`, and a new final `verify_round` requires `preArchivePassed && archived` — folding any archive failure into `findings` as `"openspec archive failed: ..."`. The fixup prompt gained an explicit remedy for the scenario-drop case: copy the ENTIRE current `### Requirement:` block (every scenario) into the delta's MODIFIED Requirements section before re-applying the intended edit. A successful archive now happens as part of the same loop iteration that reports `passed: true`, so the loop's exit condition doubles as "archived successfully" — there is no separate post-loop archive step anymore; `verify_gate` is now just a pass/fail check that `TERMINATE`s on failure.

- **A stray extra loop iteration after a successful archive crashed on a file that no longer existed.** A live run failed in `reparse_tasks` (`openspec_tasks_to_subtasks`) on iteration 2 with `No such file or directory: .../openspec/changes/harness-issue-3/tasks.md` — the change had already been archived (moved to `openspec/changes/archive/...`) by iteration 1's successful `archive_change`, yet the loop ran again and its first step unconditionally tried to re-read the now-relocated `tasks.md`. `verify_loop`'s exit condition (`$.verify_passed !== true`) is set via `verify_round_state` at the very end of the same iteration that just archived successfully, and should stop the loop from scheduling another pass — but evidently a stray iteration got scheduled anyway. Rather than chase the exact Conductor engine timing/ordering behind that (unconfirmed without a live trace), the loop body was made defensively idempotent regardless of cause: added an `archive_already_done_gate` SWITCH wrapping the *entire* existing loop body (`reparse_tasks` through `verify_action`), gated on `workflow.variables.archived`. Once a prior iteration has successfully archived, any further iteration is a single `NOOP` — no file reads, no checks, no archive re-attempt — and the loop condition (already false) stops it for good on the next evaluation. This is deliberately a belt-and-suspenders fix: it doesn't depend on understanding *why* an extra iteration might fire, only on guaranteeing that if one does, it can't touch anything.

**Archiving removed from `code_parallel` entirely.** Despite the two fixes directly above, `openspec archive` continued to be the least reliable step in the loop across live runs — each fix closed one concrete failure mode (spec validity, then the scenario-drop merge-safety check) but the class of possible archive-time failures was never actually bounded, and every newly-discovered one meant `code_parallel`'s entire run failing closed over something orthogonal to whether the *code* itself was correct. Decision 6 above was revised as a result: the `archive_attempt_gate`/`capture_archive_result`/`capture_archive_skip` machinery and the `archive_already_done_gate` wrapper (both introduced by the two fixes directly above) are removed outright, `verify_round`'s `passed` reverts to just `preArchivePassed` (real tests + semantic judge + `openspec validate`, with the `preArchivePassed` name reverting to plain `passed`), and `code_parallel` no longer archives the OpenSpec change under any circumstance. The debugging history in this section (from the spec-validity fix onward) is kept as the record of what was tried and why it didn't hold up in practice, not as the shipped design — see Decision 6 and the Goals/Non-Goals above for the current, actual behavior.

## Risks / Trade-offs

- **[Risk]** The fixup agent's derived `Bash(<token> *)` allowlist pattern is too permissive for a token that legitimately matches unrelated dangerous invocations (e.g. a `Test:` command starting with a generic token also used elsewhere). → **Mitigation:** the pattern is scoped per-subtask, applied only for the duration of that subtask's/fixup's own `coding_agent` call, and the non-bypassable worktree-write guard and OS sandbox remain in force regardless of the Bash allowlist.
- **[Risk]** Verification cost: every `code_parallel` run now pays for real test execution plus a judge call, and potentially a fixup round-trip. → **Mitigation:** bounded iteration cap (mirrors `openspecMaxIterations`); fail-closed on exhaustion avoids unbounded spend.
- **[Risk]** Compound `Test:` commands (`cd x && pytest`) won't be allow-listed by the first-token heuristic and will fail closed with a permission denial that looks like a test failure. → **Mitigation:** document the single-invocation convention for `Test:` lines (already implicitly assumed by `TASKS_RULE`'s example, `Test: pytest path/to/test_a.py`); treat broader shell-parsing as a follow-up if this proves common in practice.
- **[Risk]** Removing `openspec_change_validation`/`openspec_archive` breaks any in-flight or already-referenced usage of those task names. → **Mitigation:** grep confirms they are not yet referenced by any workflow JSON as of this change; safe to remove before they're wired anywhere.
- **[Trade-off]** A single consolidated fixup pass (Decision 4) is simpler and cheaper than targeted re-forking, but can't parallelize a fix that touches multiple independent files the way the original fan-out did. Accepted for this change; revisit if fixup rounds are frequently large.

## Migration Plan

1. Remove `openspec_change_validation`/`openspec_archive` (`openspecops/tasks.py`) and `validate_changes`/`archive` (`common/openspec_cli.py`); confirm via grep that no workflow JSON references them yet (they were added ahead of this change and never wired in).
2. Add the `verify_loop` `DO_WHILE` to `code_parallel.json` after `merge_worktrees` (real tests + semantic judge + `openspec validate`); do not add an archive step — `code_parallel` never calls `openspec_finalize`.
3. Update `code_subtask.json`'s `coding_agent` call and the new fixup `coding_agent` call to receive the explicit `allowedTools` computed from each subtask's `testCmd`.
4. Update `openspec_plan.json`'s `plan_review` `WAIT` draft to include `proposal.md` content; update `tui/widgets/modals.py` to render it.
5. Update `issue_to_pr.json` and `address_pr.json` to consume `code_parallel`'s new verification outputs in their PR-body `JSON_JQ_TRANSFORM` steps instead of their current hardcoded strings.
6. No data migration or rollback concerns beyond reverting the workflow JSON/worker changes — no persistent schema changes are introduced.

## Open Questions

**Resolved during implementation:** Used a distinct `verifyMaxIterations` input (default 3) rather than reusing `openspecMaxIterations`, since planning-approval and post-implementation-fixup are different concerns with different reasonable bounds.

- **Unresolved, and now lower-stakes:** why did `verify_loop` schedule an extra iteration after a round that already set `workflow.variables.verifyPassed = true`? The `archive_already_done_gate` defensive fix (and the archiving it was guarding) has since been removed entirely — with nothing in the loop archiving, a stray extra iteration just re-runs checks/judge/validate harmlessly against an already-verified worktree rather than crashing on a relocated `tasks.md`. The underlying Conductor timing trigger was never confirmed from a live trace and is no longer load-bearing; worth root-causing only if it turns out to waste a meaningful amount of verification cost in practice.

**Superseded:** `code_parallel` no longer calls `openspec_finalize` at all (see the revised Decision 6), so the same-repo call-shape question this entry resolved (`writebackRepoPath == writebackProjectPath == repoPath`, `sameRepo: true`, no adapter task) is moot for this change. Kept here only as a historical note; `openspec_finalize`'s same-repo behavior itself is unchanged and remains correct for `openspec_development.json`'s own use.
