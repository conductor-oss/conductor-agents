## 8. Post-implementation fixes (found running against a live sandbox repo)

Files: coding-harness/workers/openspecops/tasks.py, coding-harness/workers/tests/test_openspecops.py, coding-harness/workers/workflows/code_parallel.json, coding-harness/workers/tests/test_verify_loop_composition.py
Test: pytest coding-harness/workers/tests/test_openspecops.py coding-harness/workers/tests/test_verify_loop_composition.py coding-harness/workers/tests/test_workflows.py

See design.md's "Post-implementation fixes" section for the full analysis. These edits touch files Groups 1 and 4 already own (bug fixes to already-completed work, not new scope), plus one new test file.

Note: 8.7 and 8.8 below were later reverted — decided during a follow-up review that archiving shouldn't be attempted from `code_parallel` at all (see design.md's closing "Archiving removed from `code_parallel` entirely" note). They're rewritten below, unchecked, to describe the removal work itself rather than the archive-in-loop mechanics they originally added.

- [x] 8.1 `openspec_run_subtask_check`: catch `OSError` around the `subprocess.run` call specifically and return `passed: false` via `ok()` instead of letting the broad `except Exception` route a missing/misnamed binary through `fail()` (a hard Conductor task failure that aborted the whole run before the fixup loop ran). Added a regression test.
- [x] 8.2 `code_parallel.json`'s `verify_loop`: added a `reparse_tasks` (`openspec_tasks_to_subtasks`) call reading `${openspec_plan.output.changeDir}/tasks.md` fresh each iteration; `build_checks` now derives `checksList` and `fixupAllowedTools` from that live re-parse instead of `build_forks`'s plan-time snapshot, so a fixup agent's edit to a `Test:` line is actually re-checked on the next round instead of failing identically until the iteration cap burns out. Removed the now-unused `checksList`/`fixupAllowedTools` fields from `build_forks`'s output.
- [x] 8.3 Added `test_verify_loop_composition.py`: executes the real `build_checks` jq query (skipped if `jq` is absent) confirming it reads from `reparse_tasks` (not `build_forks`) and that a changed `testCmd` between two evaluations produces a different check command.
- [x] 8.4 `openspec_run_subtask_check`: renamed its `output` field to `log`. It collided with the codebase's established `.value.output // .value // {}` JOIN-unwrap idiom (used by `checks_summary` and `aggregate()`) — for a failing check, `.value.output` resolved to the captured-text *string* instead of falling through to the real result object, so a later `.passed` lookup indexed a string and crashed with `checks_summary__N` failing on `Cannot index string with string "passed"`. Updated the one test that referenced the old field name.
- [x] 8.5 Extended `TASKS_RULE` (`common/openspec_cli.py`) to tell the tasks-artifact-writing agent what the coding agent is actually permitted to run: `Test:` must be exactly one program invocation, no shell pipes/`&&`/`$(...)`/`test`, naming `pytest`/`npm`/`npx`/`go`/`cargo`/`node`/`python3` (not `python`) as the concretely-allowed runners. This closes the loop at the source instead of continuing to patch downstream failures — a live run had produced `Test: test "$(python hello.py)" = ... && ...`, which was denied outright since `test`/`&&`/`$(...)` were never permitted. Also added a short complementary note to `verify_judge`'s and `verify_fixup`'s prompts in `code_parallel.json` so a still-malformed legacy `Test:` line is correctly attributed (and simplified, not worked around) if one slips through. Added a test asserting the new guidance's key phrases are present in `TASKS_RULE`.
- [x] 8.6 Added `openspec_validate_change` (`openspecops/tasks.py` + taskdef): runs `openspec validate <id> --strict` for real and reports `{valid, issues}` gracefully via `ok()`, never raising. Wired it into `code_parallel.json`'s `verify_loop` as a `validate_spec` task run every iteration alongside the real test commands and semantic judge; `verify_round`'s `passed` now requires `checks.allPassed && judge.passed && specValid`, folding a validate failure into `findings` as `"OpenSpec validate failed: <issues>"` so the fixup pass fixes the flagged OpenSpec artifact instead of the whole workflow crashing when `archive_change` (openspec_finalize) later ran the same validate and raised. Added unit tests for the new task and jq-execution tests locking in the updated `verify_round` gate.
- [x] 8.7 **Revised — reverses the original 8.7.** (Original: after `openspec_validate_change` passed, `openspec archive` still crashed the workflow on a live run — `current spec contains scenario(s) not present in the modified block`, an archive-time-only merge-safety check `openspec validate` doesn't perform — so archiving was restructured to run *inside* `verify_loop` via an `archive_attempt_gate` SWITCH, `openspec_finalize` as `archive_change` marked `optional: true`, `capture_archive_result`/`capture_archive_skip`, and a `preArchivePassed && archived` gate.) That machinery is now removed entirely: delete `archive_attempt_gate`, the `archive_change` (`openspec_finalize`) call, `capture_archive_result`/`capture_archive_skip`, the workflow variables `archiveAttempted`/`archived`/`archivePath`/`archiveBranch`/`archiveCommit`/`archiveError`, the `"openspec archive failed: ..."` finding path, and the fixup prompt's scenario-drop remedy. Restore `verify_round`'s `passed` (renaming `preArchivePassed` back to `passed`) to just `checks.allPassed && judge.passed && specValid` — no archive dependency. Reason: `openspec archive` was the least reliable step across live runs (see design.md's closing note on this decision) and archiving isn't on the critical path of shipping a correct PR; it's now a manual step a human runs after merging. Update `test_verify_loop_composition.py` accordingly.
- [x] 8.8 **Revised — reverses the original 8.8.** (Original: a stray extra loop iteration after a successful archive crashed `reparse_tasks` on a relocated `tasks.md`, fixed by wrapping the entire loop body in an `archive_already_done_gate` SWITCH that no-ops once `workflow.variables.archived` is true.) Remove that `archive_already_done_gate` SWITCH wrapper entirely — it only ever guarded against re-touching an already-archived change, which can't happen once nothing in the loop archives; the loop body (`reparse_tasks` through `verify_action`) runs unconditionally each iteration again, as it did before the original 8.7/8.8. Remove `test_loop_body_is_a_noop_once_the_change_is_already_archived` (or repurpose it if the underlying stray-iteration timing question — still unresolved, see design.md's Open Questions — is ever root-caused independent of archiving).
